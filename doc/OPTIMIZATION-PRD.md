# Roamly 商业闭环优化 PRD

## 1. 文档目的

本 PRD 将现有旅行规划、笔记、旅程和社区能力推进到可运营的商业产品。实施选择方案 B：先完成统一身份、资源权限、计划持久化和稳定性建设，再补齐运营和商业化能力。

本文前半部分定义目标、方案和实施顺序；后半部分记录当前差距、待解决问题和验收标准。

## 2. 当前产品与商业产品的差距

当前产品已经形成“发现灵感 → AI 规划 → 保存笔记/旅程 → 社区发布 → 来源追踪”的功能骨架，适合产品演示。

完整商业闭环还需要以下能力：

1. **身份闭环**：每个计划、笔记、旅程、任务和审核动作都必须绑定真实用户和角色。
2. **数据闭环**：AI 计划需要服务端持久化、版本、状态和可恢复任务，不能只依赖浏览器或短期 Redis 状态。
3. **体验闭环**：计划生成后要能编辑、保存、再次打开、分享、出行中更新、出行后沉淀为笔记。
4. **内容闭环**：发布、复制、协作、举报、审核、申诉和来源追踪要有可执行的状态机。
5. **运营闭环**：要能统计生成率、保存率、复用率、发布率、审核准确率和 AI 成本。
6. **收入闭环**：当前 PRD 不包含酒店、门票、交通、支付和订单。若要形成商业收入，需要增加预订/联盟链接、归因、佣金或会员额度。

## 3. 目标用户与核心路径

### 3.1 目标角色

| 角色 | 目标 |
|---|---|
| 规划用户 | 输入目的地、日期、预算和偏好，得到可执行计划并保存 |
| 出行用户 | 在旅途中查看、调整和记录行程 |
| 内容创作者 | 将完成的旅程整理成笔记并发布 |
| 社区用户 | 浏览、收藏、复制和协作改写他人的路线 |
| 平台审核员 | 处理版权相似、举报和低信誉内容 |
| 运营/商业角色 | 查看转化、供应商、成本和收入数据 |

### 3.2 目标业务流程

```text
注册/登录
  ↓
发现灵感或创建 AI 计划
  ↓
生成任务持久化，计划可恢复、可编辑、可版本化
  ↓
保存为灵感 / 旅程 / 数据库笔记
  ↓
出行中更新点位、花费、照片和记录
  ↓
出行完成，生成旅行笔记
  ↓
发布社区，经过来源检查、相似度判断和人工审核
  ↓
其他用户收藏、复制、协作或进入新的 AI 规划
  ↓
商业转化：预订、联盟链接、会员额度或增值服务
  ↓
行为数据和收入数据回流，用于推荐和产品优化
```

## 4. 方案 B：稳健产品化方案

### 4.1 统一身份与权限

- 统一从已验证 Token 获取 `currentUserId`，删除生产接口中的 `userId`、`reporterId`、`from` 和 `reviewerId` 身份参数。
- 引入 `USER`、`MODERATOR`、`ADMIN` 角色。
- 所有资源查询、更新、删除在服务层再次校验所有权。
- 子资源点位、图片、评论、修订记录必须通过父资源校验归属。
- 平台审核只允许 `MODERATOR` 或 `ADMIN`。

### 4.2 AI 计划与任务中心

- 增加计划主表、计划版本表和任务表。
- A2A 任务必须绑定用户、状态、输入快照、输出快照、错误原因和创建时间。
- 任务支持幂等键、取消、重试、过期和恢复。
- 统一 A2A 规划与旧版结构化规划接口，移除失效的流式接口。
- 所有输入增加范围校验；按用户、IP 和供应商设置额度。

### 4.3 保存与旅程生命周期

- 提供后端原子接口：一次请求完成“保存计划 + 创建灵感/旅程 + 写入点位”。
- 计划状态：`DRAFT`、`SAVED`、`IN_TRIP`、`COMPLETED`、`PUBLISHED`。
- 支持计划版本和重新规划，保留旧版本。
- 日期、时间、时区使用明确的数据模型，不能把活动时间写入日期字段。

### 4.4 笔记、分享和社区

- 数据库笔记是发布唯一来源；本地文件必须显式导入。
- 分享支持生成、复制、撤销、过期和访问日志。
- 社区帖子状态：`DRAFT`、`PENDING_REVIEW`、`PUBLISHED`、`REJECTED`、`ARCHIVED`。
- 复制和协作保留来源、版本和贡献者关系。
- 举报、审核、申诉形成可追踪记录。

### 4.5 安全与部署

- 删除默认数据库、Redis、邮件和 AI 凭据。
- MySQL、Redis、MCP 和 A2A 只加入内部网络；公网只暴露网关。
- 关闭验证码、Authorization、原始请求体和异常堆栈的敏感日志。
- 文件上传校验 MIME、文件头、大小和扩展名，使用对象存储或独立静态域名。
- 统一 CORS、CSP、Cookie 和 Token 策略。

### 4.6 运营和商业化

- 埋点：注册、首次规划、计划完成、保存、再次打开、出行完成、发布、复制、举报、审核和商业点击。
- 成本：记录每次模型调用、工具耗时、失败原因和供应商成本。
- 商业入口：预订链接、联盟商品、会员额度、企业定制或高级计划模板。
- 收入归因：计划、目的地、供应商、用户和订单之间建立可追踪关系。

## 5. 实施顺序

### 阶段一：安全止血与身份统一

1. 统一当前用户上下文。
2. 修复用户、旅程、笔记、社区和审核接口的资源归属。
3. 保护 Agent、问卷和 A2A 任务。
4. 增加审核员角色。
5. 关闭匿名上传、默认凭据和公网内部端口。

### 阶段二：计划持久化与保存闭环

1. 增加计划和任务持久化模型。
2. 将 AI 结果保存改为后端原子操作。
3. 修复日期、时间、时区和点位数据模型。
4. 增加版本、恢复、重试和幂等。

### 阶段三：内容与运营闭环

1. 完成分享、编辑、审核和申诉界面。
2. 增加埋点、成本统计和运营后台。
3. 迁移历史 `user_001` 数据并清理兼容接口。

### 阶段四：商业收入闭环

1. 选择预订、联盟、会员或企业服务中的第一条收入路径。
2. 建立点击、转化、订单和佣金归因。
3. 增加配额、权益、退款和客服流程。

## 6. 后半部分：当前待解决问题

### 6.1 已确认的代码问题

- 多个用户接口从 query/body 接收用户身份，服务层存在按 ID 直接读写资源的路径。
- 平台审核没有角色校验。
- Agent 消息、历史、工具结果和删除接口缺少会话所有权校验。
- A2A 任务没有用户归属、输入校验和调用额度。
- `/api/user/upload` 可匿名调用，头像上传信任原始扩展名。
- Docker Compose 暴露内部端口并保留默认数据库密码。
- 邮箱验证码写入日志，系统异常返回内部异常信息。
- 前端 AI 保存使用固定 `user_001`。
- 前端把活动时间传给 `LocalDate` 点位字段。
- AI 规划、保存、灵感和旅程之间没有后端事务。
- 分享链接、编辑、审核后台和地理编码仍不完整。

### 6.2 待产品决策问题

- 第一条收入路径选择预订联盟、会员额度、企业定制还是付费模板。
- 社区帖子是否允许匿名查看，分享链接是否允许匿名访问。
- 原作者能否关闭复制、限制协作或要求署名。
- AI 规划免费额度、会员额度和超额计费规则。
- 审核员的权限范围、审核时效、申诉和通知方式。

### 6.3 验收标准

- 用户 A 无法读取、修改、删除用户 B 的任意笔记、旅程、点位、图片和会话。
- 普通用户无法发布冒充他人的帖子，也无法调用平台审核接口。
- 未登录请求无法创建 A2A、Agent 问卷或社区发布任务。
- 一个 AI 计划可以恢复、编辑、保存、重新打开并生成旅程点位。
- 保存失败时不会留下半成品数据；重复请求不会产生重复计划。
- 所有敏感凭据由环境或密钥管理系统注入，内部服务不暴露公网。
- 能统计从首次规划到保存、出行完成、发布和商业点击的完整漏斗。

### 2026-09-27 企业级闭环差距复盘

#### 当前已经形成的闭环

当前版本已经具备一条可演示的产品链路：用户登录 → 提交旅行需求 → AI 生成计划 → 用户保存为笔记或行程 → 进入社区发布、复制、审核和举报流程。阶段一已补充资源归属校验、A2A 输入校验、AI 结果基础校验、原子保存、上传限制和部分部署安全约束。

这条链路可以作为 MVP 基础，但还不能作为企业生产闭环。生成任务、计划版本、质量证据、运营指标和商业结果之间还没有形成可查询、可恢复、可审计的统一业务主线。

#### 仍未达到企业级的关键差距

1. **任务和计划没有可靠落库**：A2A 状态主要依赖 Redis，任务 24 小时过期；数据库中没有完整的任务输入快照、输出快照、重试次数、幂等键、模型版本、提示词版本、工具调用记录和计划版本链。服务重启、重复提交和长任务恢复仍存在风险。
2. **AI 质量闭环不完整**：已有结构校验和超时控制，但没有供应商降级与熔断、死信和人工恢复、提示词/模型版本登记、评测集回归、事实来源引用、用户反馈到质量指标的闭环，也没有统一的提示注入和敏感内容策略。
3. **身份治理还不是企业权限体系**：当前主要是登录用户和资源归属校验，审核员通过配置用户 ID 识别。缺少组织/租户、RBAC、权限变更审计、管理员后台、配额和按租户隔离，不能支撑团队客户和运营人员协作。
4. **可观测性和成本核算缺失**：没有统一 trace/correlation ID、指标、链路追踪、模型 token 与费用台账、AI 供应商成本分摊、SLO/告警和业务漏斗事件。出现慢请求、成本异常或生成质量下降时，无法快速定位和核算。
5. **旅行计划生命周期没有闭合**：目前偏重“生成并保存”，缺少草稿、确认、出行中、已完成、发布等状态，缺少版本比较/恢复、时区和事件时间统一、行程变更记录、出行中更新，以及行程结束后的自动总结和复购触达。
6. **社区治理仍是功能骨架**：已有发布、复制、修订、举报和审核相关能力，但审核队列、申诉、通知、撤回/过期分享、访问日志、内容溯源和版权处理没有形成完整运营工作台。
7. **商业化链路基本为空**：尚未发现订单、支付、退款、会员/权益、优惠、供应商/联盟、佣金结算、发票、对账和 webhook 幂等处理。当前“用户生成并保存内容”不等于可计费、可交付、可售后。
8. **数据治理和生产运维不足**：缺少敏感数据清理与导出、保留期限、删除策略、密钥轮换、备份恢复演练、迁移回滚、CI/CD 质量门禁、压测和故障演练。上传校验还需要补充文件内容/MIME 检测和对象存储隔离。

#### 下一轮实施顺序

- **P0：先让系统可重复构建和可恢复运行**：固定 JDK 17、Maven/Node 构建链路，恢复 Spring AI milestone 等依赖解析；建立 `ai_task`、`ai_plan`、`ai_plan_version` 和 outbox/幂等模型，Redis 只做缓存和实时状态。
- **P0：补齐权限和审计**：组织/租户、RBAC、管理员和审核员角色、敏感操作审计事件、租户级配额。
- **P1：补齐 AI 质量与运营闭环**：模型/提示词版本、供应商降级、重试与死信、人工恢复、评测集、引用与反馈、指标/链路/成本台账。
- **P1：补齐旅行与内容生命周期**：计划状态机、版本恢复、出行中更新、完成后总结、审核队列、申诉和通知。
- **P2：实现可交易商业闭环**：商品/供应商、订单、支付、退款、权益、佣金、对账和售后，再把推荐和运营漏斗接入数据分析。

在以上项目完成前，本项目适合定位为“具备安全基础的 AI 旅行规划 MVP”，不宜宣称已经达到企业级 AI 应用闭环。

## 8. 本轮企业闭环实现记录（2026-09-27）

本节记录本轮已经写入代码的实现，前面的“差距复盘”作为改造前基线保留。

### 8.1 AI 任务、计划和事件链路

本轮新增 `data/enterprise_ai_migration.sql`，建立以下业务事实表：

- `ai_task`：保存用户、租户、幂等键、输入快照、状态、进度、尝试次数、输出快照和错误信息。
- `ai_plan`：保存计划主实体和旅行生命周期状态：`DRAFT → CONFIRMED → IN_TRIP → COMPLETED → PUBLISHED → ARCHIVED`。
- `ai_plan_version`：保存不可变的请求、结果、质量状态、模型、提示词版本和警告快照。
- `ai_audit_event`：保存计划创建、状态变化等敏感操作及 trace ID。
- `ai_usage_ledger`：保存供应商、模型、延迟和后续费用核算字段。
- `ai_outbox_event`：保存计划创建事件，后续通知、推荐、商业归因和运营分析均从事件消费。

实现链路为：

```text
HTTP 请求
  → Idempotency-Key 按用户去重
  → ai_task 落库
  → Redis 镜像实时进度
  → A2A 工具编排和结构化校验
  → ai_plan + ai_plan_version + ai_usage_ledger + ai_audit_event + ai_outbox_event 同事务写入
  → SSE 返回 planId
  → 前端保存笔记时回传 planId
  → 后续出行状态、分享和商业订单都按 planId 关联
```

`TaskStateStore` 现在优先从数据库恢复任务，Redis 只用于实时进度和 SSE；SSE 重连读取已完成版本，不会再次调用模型。数据库迁移未执行时仍保留开发环境 Redis 降级，但生产发布必须把迁移成功作为前置条件。

### 8.2 商业化链路

新增 `travel-module-commerce-biz`，第一条收入路径采用“联盟商品点击归因 + 订单 + 支付事件 + 权益”：

1. `commerce_offer` 保存供应商商品、跳转地址、价格和佣金比例。
2. `/api/commerce/offers` 按计划归属和目的地返回商品。
3. `/api/commerce/clicks` 写入点击和 attribution code。
4. `/api/commerce/orders` 使用 `Idempotency-Key` 创建订单。
5. `/api/commerce/orders/{orderNo}/pay` 通过 `PaymentGateway` 端口处理支付，支付事件按 eventId 幂等落库。
6. 支付成功后写入 `commerce_entitlement`，订单状态变为 `PAID`。
7. `/api/commerce/orders/{orderNo}/cancel` 支持待支付订单取消，订单和计划可以通过 `planId` 对账。

前端 `ChatView` 在收到真实 `planId` 后加载匹配商品，点击商品会顺序执行点击归因、幂等建单和沙箱支付，成功后提示权益已写入账户。前端展示明确标注为沙箱链路，避免把演示支付当成真实扣款。

本地验收使用 `SandboxPaymentGateway`，它只生成沙箱支付事件，不代表真实资金扣款。生产环境需要替换为经过签名校验、回调验签、退款和对账的真实供应商适配器，并关闭沙箱开关。
