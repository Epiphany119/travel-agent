# Roamly 商业闭环优化 PRD

## 1. 文档目的

本 PRD 将现有旅行规划、笔记、旅程和社区能力推进到可运营的商业产品。实施选择方案 B：先完成统一身份、资源权限、计划持久化和稳定性建设，再补齐运营和商业化能力。

本文前半部分定义目标、方案和实施顺序；后半部分记录当前差距、待解决问题和验收标准。

## 2. 当前产品与商业产品的差距

当前产品已经形成“发现灵感 → AI 规划 → 保存笔记/旅程 → 社区发布 → 来源追踪”的功能骨架，适合产品演示。

完整商业闭环还需要以下能力：

1. **身份闭环**：每个计划、笔记、旅程、任务和审核动作都必须绑定真实用户和角色。
2. **数据闭环**：AI 计划需要服务端持久化、版本、状态和可恢复任务，不能只依赖浏览器或短期 Redis 状态。
3. **体验闭环**：计划生成后要能编辑、保存、再次打开、分享、出行中更新、出行后沉淀为笔记。
4. **内容闭环**：发布、复制、协作、举报、审核、申诉和来源追踪要有可执行的状态机。
5. **运营闭环**：要能统计生成率、保存率、复用率、发布率、审核准确率和 AI 成本。
6. **收入闭环**：当前 PRD 不包含酒店、门票、交通、支付和订单。若要形成商业收入，需要增加预订/联盟链接、归因、佣金或会员额度。

## 3. 目标用户与核心路径

### 3.1 目标角色

| 角色 | 目标 |
|---|---|
| 规划用户 | 输入目的地、日期、预算和偏好，得到可执行计划并保存 |
| 出行用户 | 在旅途中查看、调整和记录行程 |
| 内容创作者 | 将完成的旅程整理成笔记并发布 |
| 社区用户 | 浏览、收藏、复制和协作改写他人的路线 |
| 平台审核员 | 处理版权相似、举报和低信誉内容 |
| 运营/商业角色 | 查看转化、供应商、成本和收入数据 |

### 3.2 目标业务流程

```text
注册/登录
  ↓
发现灵感或创建 AI 计划
  ↓
生成任务持久化，计划可恢复、可编辑、可版本化
  ↓
保存为灵感 / 旅程 / 数据库笔记
  ↓
出行中更新点位、花费、照片和记录
  ↓
出行完成，生成旅行笔记
  ↓
发布社区，经过来源检查、相似度判断和人工审核
  ↓
其他用户收藏、复制、协作或进入新的 AI 规划
  ↓
商业转化：预订、联盟链接、会员额度或增值服务
  ↓
行为数据和收入数据回流，用于推荐和产品优化
```

## 4. 方案 B：稳健产品化方案

### 4.1 统一身份与权限

- 统一从已验证 Token 获取 `currentUserId`，删除生产接口中的 `userId`、`reporterId`、`from` 和 `reviewerId` 身份参数。
- 引入 `USER`、`MODERATOR`、`ADMIN` 角色。
- 所有资源查询、更新、删除在服务层再次校验所有权。
- 子资源点位、图片、评论、修订记录必须通过父资源校验归属。
- 平台审核只允许 `MODERATOR` 或 `ADMIN`。

### 4.2 AI 计划与任务中心

- 增加计划主表、计划版本表和任务表。
- A2A 任务必须绑定用户、状态、输入快照、输出快照、错误原因和创建时间。
- 任务支持幂等键、取消、重试、过期和恢复。
- 统一 A2A 规划与旧版结构化规划接口，移除失效的流式接口。
- 所有输入增加范围校验；按用户、IP 和供应商设置额度。

### 4.3 保存与旅程生命周期

- 提供后端原子接口：一次请求完成“保存计划 + 创建灵感/旅程 + 写入点位”。
- 计划状态：`DRAFT`、`SAVED`、`IN_TRIP`、`COMPLETED`、`PUBLISHED`。
- 支持计划版本和重新规划，保留旧版本。
- 日期、时间、时区使用明确的数据模型，不能把活动时间写入日期字段。

### 4.4 笔记、分享和社区

- 数据库笔记是发布唯一来源；本地文件必须显式导入。
- 分享支持生成、复制、撤销、过期和访问日志。
- 社区帖子状态：`DRAFT`、`PENDING_REVIEW`、`PUBLISHED`、`REJECTED`、`ARCHIVED`。
- 复制和协作保留来源、版本和贡献者关系。
- 举报、审核、申诉形成可追踪记录。

### 4.5 安全与部署

- 删除默认数据库、Redis、邮件和 AI 凭据。
- MySQL、Redis、MCP 和 A2A 只加入内部网络；公网只暴露网关。
- 关闭验证码、Authorization、原始请求体和异常堆栈的敏感日志。
- 文件上传校验 MIME、文件头、大小和扩展名，使用对象存储或独立静态域名。
- 统一 CORS、CSP、Cookie 和 Token 策略。

### 4.6 运营和商业化

- 埋点：注册、首次规划、计划完成、保存、再次打开、出行完成、发布、复制、举报、审核和商业点击。
- 成本：记录每次模型调用、工具耗时、失败原因和供应商成本。
- 商业入口：预订链接、联盟商品、会员额度、企业定制或高级计划模板。
- 收入归因：计划、目的地、供应商、用户和订单之间建立可追踪关系。

## 5. 实施顺序

### 阶段一：安全止血与身份统一

1. 统一当前用户上下文。
2. 修复用户、旅程、笔记、社区和审核接口的资源归属。
3. 保护 Agent、问卷和 A2A 任务。
4. 增加审核员角色。
5. 关闭匿名上传、默认凭据和公网内部端口。

### 阶段二：计划持久化与保存闭环

1. 增加计划和任务持久化模型。
2. 将 AI 结果保存改为后端原子操作。
3. 修复日期、时间、时区和点位数据模型。
4. 增加版本、恢复、重试和幂等。

### 阶段三：内容与运营闭环

1. 完成分享、编辑、审核和申诉界面。
2. 增加埋点、成本统计和运营后台。
3. 迁移历史 `user_001` 数据并清理兼容接口。

### 阶段四：商业收入闭环

1. 选择预订、联盟、会员或企业服务中的第一条收入路径。
2. 建立点击、转化、订单和佣金归因。
3. 增加配额、权益、退款和客服流程。

## 6. 后半部分：当前待解决问题

### 6.1 已确认的代码问题

- 多个用户接口从 query/body 接收用户身份，服务层存在按 ID 直接读写资源的路径。
- 平台审核没有角色校验。
- Agent 消息、历史、工具结果和删除接口缺少会话所有权校验。
- A2A 任务没有用户归属、输入校验和调用额度。
- `/api/user/upload` 可匿名调用，头像上传信任原始扩展名。
- Docker Compose 暴露内部端口并保留默认数据库密码。
- 邮箱验证码写入日志，系统异常返回内部异常信息。
- 前端 AI 保存使用固定 `user_001`。
- 前端把活动时间传给 `LocalDate` 点位字段。
- AI 规划、保存、灵感和旅程之间没有后端事务。
- 分享链接、编辑、审核后台和地理编码仍不完整。

### 6.2 待产品决策问题

- 第一条收入路径选择预订联盟、会员额度、企业定制还是付费模板。
- 社区帖子是否允许匿名查看，分享链接是否允许匿名访问。
- 原作者能否关闭复制、限制协作或要求署名。
- AI 规划免费额度、会员额度和超额计费规则。
- 审核员的权限范围、审核时效、申诉和通知方式。

### 6.3 验收标准

- 用户 A 无法读取、修改、删除用户 B 的任意笔记、旅程、点位、图片和会话。
- 普通用户无法发布冒充他人的帖子，也无法调用平台审核接口。
- 未登录请求无法创建 A2A、Agent 问卷或社区发布任务。
- 一个 AI 计划可以恢复、编辑、保存、重新打开并生成旅程点位。
- 保存失败时不会留下半成品数据；重复请求不会产生重复计划。
- 所有敏感凭据由环境或密钥管理系统注入，内部服务不暴露公网。
- 能统计从首次规划到保存、出行完成、发布和商业点击的完整漏斗。

### 2026-09-27 企业级闭环差距复盘

#### 当前已经形成的闭环

当前版本已经具备一条可演示的产品链路：用户登录 → 提交旅行需求 → AI 生成计划 → 用户保存为笔记或行程 → 进入社区发布、复制、审核和举报流程。阶段一已补充资源归属校验、A2A 输入校验、AI 结果基础校验、原子保存、上传限制和部分部署安全约束。

这条链路可以作为 MVP 基础，但还不能作为企业生产闭环。生成任务、计划版本、质量证据、运营指标和商业结果之间还没有形成可查询、可恢复、可审计的统一业务主线。

#### 仍未达到企业级的关键差距

1. **任务和计划没有可靠落库**：A2A 状态主要依赖 Redis，任务 24 小时过期；数据库中没有完整的任务输入快照、输出快照、重试次数、幂等键、模型版本、提示词版本、工具调用记录和计划版本链。服务重启、重复提交和长任务恢复仍存在风险。
2. **AI 质量闭环不完整**：已有结构校验和超时控制，但没有供应商降级与熔断、死信和人工恢复、提示词/模型版本登记、评测集回归、事实来源引用、用户反馈到质量指标的闭环，也没有统一的提示注入和敏感内容策略。
3. **身份治理还不是企业权限体系**：当前主要是登录用户和资源归属校验，审核员通过配置用户 ID 识别。缺少组织/租户、RBAC、权限变更审计、管理员后台、配额和按租户隔离，不能支撑团队客户和运营人员协作。
4. **可观测性和成本核算缺失**：没有统一 trace/correlation ID、指标、链路追踪、模型 token 与费用台账、AI 供应商成本分摊、SLO/告警和业务漏斗事件。出现慢请求、成本异常或生成质量下降时，无法快速定位和核算。
5. **旅行计划生命周期没有闭合**：目前偏重“生成并保存”，缺少草稿、确认、出行中、已完成、发布等状态，缺少版本比较/恢复、时区和事件时间统一、行程变更记录、出行中更新，以及行程结束后的自动总结和复购触达。
6. **社区治理仍是功能骨架**：已有发布、复制、修订、举报和审核相关能力，但审核队列、申诉、通知、撤回/过期分享、访问日志、内容溯源和版权处理没有形成完整运营工作台。
7. **商业化链路基本为空**：尚未发现订单、支付、退款、会员/权益、优惠、供应商/联盟、佣金结算、发票、对账和 webhook 幂等处理。当前“用户生成并保存内容”不等于可计费、可交付、可售后。
8. **数据治理和生产运维不足**：缺少敏感数据清理与导出、保留期限、删除策略、密钥轮换、备份恢复演练、迁移回滚、CI/CD 质量门禁、压测和故障演练。上传校验还需要补充文件内容/MIME 检测和对象存储隔离。

#### 下一轮实施顺序

- **P0：先让系统可重复构建和可恢复运行**：固定 JDK 17、Maven/Node 构建链路，恢复 Spring AI milestone 等依赖解析；建立 `ai_task`、`ai_plan`、`ai_plan_version` 和 outbox/幂等模型，Redis 只做缓存和实时状态。
- **P0：补齐权限和审计**：组织/租户、RBAC、管理员和审核员角色、敏感操作审计事件、租户级配额。
- **P1：补齐 AI 质量与运营闭环**：模型/提示词版本、供应商降级、重试与死信、人工恢复、评测集、引用与反馈、指标/链路/成本台账。
- **P1：补齐旅行与内容生命周期**：计划状态机、版本恢复、出行中更新、完成后总结、审核队列、申诉和通知。
- **P2：实现可交易商业闭环**：商品/供应商、订单、支付、退款、权益、佣金、对账和售后，再把推荐和运营漏斗接入数据分析。

在以上项目完成前，本项目适合定位为“具备安全基础的 AI 旅行规划 MVP”，不宜宣称已经达到企业级 AI 应用闭环。

## 8. 本轮企业闭环实现记录（2026-09-27）

本节记录本轮已经写入代码的实现，前面的“差距复盘”作为改造前基线保留。

### 8.1 AI 任务、计划和事件链路

本轮新增 `data/enterprise_ai_migration.sql`，建立以下业务事实表：

- `ai_task`：保存用户、租户、幂等键、输入快照、状态、进度、尝试次数、输出快照和错误信息。
- `ai_plan`：保存计划主实体和旅行生命周期状态：`DRAFT → CONFIRMED → IN_TRIP → COMPLETED → PUBLISHED → ARCHIVED`。
- `ai_plan_version`：保存不可变的请求、结果、质量状态、模型、提示词版本和警告快照。
- `ai_audit_event`：保存计划创建、状态变化等敏感操作及 trace ID。
- `ai_usage_ledger`：保存供应商、模型、延迟和后续费用核算字段。
- `ai_outbox_event`：保存计划创建事件，后续通知、推荐、商业归因和运营分析均从事件消费。

实现链路为：

```text
HTTP 请求
  → Idempotency-Key 按用户去重
  → ai_task 落库
  → Redis 镜像实时进度
  → A2A 工具编排和结构化校验
  → ai_plan + ai_plan_version + ai_usage_ledger + ai_audit_event + ai_outbox_event 同事务写入
  → SSE 返回 planId
  → 前端保存笔记时回传 planId
  → 后续出行状态、分享和商业订单都按 planId 关联
```

`TaskStateStore` 现在优先从数据库恢复任务，Redis 只用于实时进度和 SSE；SSE 重连读取已完成版本，不会再次调用模型。数据库迁移未执行时仍保留开发环境 Redis 降级，但生产发布必须把迁移成功作为前置条件。

### 8.2 商业化链路

新增 `travel-module-commerce-biz`，第一条收入路径采用“联盟商品点击归因 + 订单 + 支付事件 + 权益”：

1. `commerce_offer` 保存供应商商品、跳转地址、价格和佣金比例。
2. `/api/commerce/offers` 按计划归属和目的地返回商品。
3. `/api/commerce/clicks` 写入点击和 attribution code。
4. `/api/commerce/orders` 使用 `Idempotency-Key` 创建订单。
5. `/api/commerce/orders/{orderNo}/pay` 通过 `PaymentGateway` 端口处理支付，支付事件按 eventId 幂等落库。
6. 支付成功后写入 `commerce_entitlement`，订单状态变为 `PAID`。

### 9.2 P0：AI 计划关联的资源所有权校验

现状复核发现，用户保存 AI 计划时，服务端对请求中的 planId 做了格式验证，但仍需确认该计划确实归属于当前认证用户。客户端提交的 planId 只作为资源标识，不能作为所有权证明。

处理规则：

- 从认证上下文获取 currentUserId；服务端查询 planId 对应计划，并验证 ownerId 与 currentUserId 一致。
- 计划不存在或不属于当前用户时拒绝操作；可统一返回“资源不存在或无权操作”，避免泄露资源是否存在。
- 所有保存入口复用同一授权服务；在笔记、灵感、旅程和计划版本关联处都执行检查。
- 对被拒绝的跨用户访问记录不包含敏感正文的安全审计信息。

验收：用户 A 可关联自己的计划；不能将用户 B 的 planId 关联到自己的笔记/旅程；不存在的 planId 被拒绝；单元/服务测试覆盖允许和拒绝路径。若当前数据库迁移未执行，先完成可运行的代码级测试，数据库端到端验收留到持久层阶段。

### 9.3 P0：任务幂等与 SSE 重连协议

当前 SSE 入口仍存在创建任务与读取流混在一起的风险；其中 GET 流路径没有使用创建请求的幂等键。建议统一为“POST 创建、GET 订阅”：

```text
POST /a2a/tasks + Idempotency-Key
  → 按当前用户与幂等键创建或取回同一任务
  → 返回 taskId
GET /a2a/tasks/{taskId}/stream
  → 校验任务所有者并订阅进度
  → 断线后重放已有事件/终态结果，不再执行模型
```

幂等规则：同一用户、同一键、同一请求体返回同一任务；同一键但请求体不同返回冲突；用户之间的键空间隔离。事件应带有可重放的顺序号或版本，客户端重连时能继续接收而不重复展示终态。

分期约束：可以先在现有任务状态设施上验证协议和重复请求行为，但 Redis/进程内状态不等同于可靠持久化。服务进程重启后的恢复、任务和幂等键长期留存、清理策略及数据库唯一约束，全部留待持久层改造，并在真实 MySQL/Redis 环境验收。

验收：重复点击不触发第二次模型规划；相同幂等键和相同输入返回原 taskId；同键不同输入被拒绝；SSE 重连不会重新生成；跨用户读取 taskId 被拒绝。

### 9.4 P1：AI 用户反馈与质量评估闭环

#### 事件与关联关系

反馈至少关联 taskId、planId、planVersion、ownerId、发生时间，并记录模型/供应商、提示词版本、工具版本、结果校验状态及降级/修复情况。业务事件覆盖：规划开始/成功/失败、工具调用结果、校验/修复/降级、查看与保存、确认采用、出行开始/完成、用户反馈、发布。记录遵循最小化原则，不把不必要的个人信息或完整敏感输入放入指标标签。

第一版用户反馈采用“有帮助/没帮助 + 可选原因”；行程完成后再收集是否采用、是否完成和计划偏差。反馈只进入质量评估与人工复盘，不默认用于模型训练。

#### 质量回路

```text
记录任务与工具结果
  → 汇总计划保存/确认/出行完成及用户反馈
  → 按模型、提示词、工具版本分析质量和成本
  → 人工复核低评分、校验失败和降级样本
  → 纳入离线评测集并运行回归
  → 小流量验证新版本
  → 对照质量、时延与成本指标决定推广或回滚
```

首批指标：任务成功率、结构校验通过率、修复与降级率、工具成功率、规划耗时、保存/确认率、行程完成率、用户评价分布及单次成功规划成本。应区分业务采用指标与模型技术指标，避免单独以生成成功率代表用户价值。

验收：反馈能指向明确计划版本；指标可以按模型/提示词/工具版本对比；人工抽样结论可进入版本化离线评测集；上线前可做回归对比；未持久化前仅算接口/埋点准备，不算反馈闭环完成。

### 9.5 P1：RBAC 与租户隔离分阶段实施

认证回答“请求来自谁”，授权回答“此用户能对该资源做什么”。服务端授权必须结合当前用户、角色、资源所有者和操作类型，不接受客户端自行声明的 ownerId、role 或 tenantId 作为授权依据。

第一阶段按当前个人旅行产品落实角色基线：

| 角色 | 范围 |
|---|---|
| USER | 管理自己的计划、笔记、旅程和反馈 |
| MODERATOR | 处理内容举报与审核；不因此获得读取所有私有旅行计划的权限 |
| ADMIN | 平台级配置及管理操作；敏感操作必须审计 |

把现有按用户 ID 配置识别审核员的方式纳入迁移计划，逐步改为服务端明确的角色授权，并定义角色授予/撤销审计。资源读取、修改、删除、分享、审核和计划关联都复用统一授权规则。

租户决策：当前先按单租户/B2C 运行，强化用户级资源隔离；不在本轮改数据库结构。只有确定面向企业团队空间后，才进入多租户实施：从认证后的成员关系建立可信 tenant context，所有读写按 tenant 范围约束，验证 tenant 间资源不可见，并配置租户管理员、成员角色、配额和审计。该阶段需要数据表、索引、迁移和旧数据归属策略，属于后续持久层工作。

验收：普通用户不能执行审核/管理操作；审核员不能越权访问私有行程；资源所有者校验在服务层执行；未来启用租户时，跨租户读写全部拒绝且有集成测试。多租户验收不能仅靠前端隐藏按钮或 Controller 路由限制。

### 9.6 P1：运营追踪、成本口径与事件处理

- 延续 `X-Trace-Id`，让 HTTP 请求、任务、模型调用、MCP/工具调用、计划保存和审计记录能够串联；对外部传入的 trace 值做长度/字符校验。
- 从模型响应采集真实输入/输出 Token、供应商、模型、延迟和请求结果；只有无法取得 Token 时才保存估算值，并明确标注 estimated，禁止把估算伪装成账单真实值。
- 按模型价格配置版本计算成本，保留原始用量与价格版本以便重算；成本事件关联 task/plan，但不把用户标识、planId 等高基数字段放进 Prometheus 标签。
- 指标端点继续限制在受信网络；看板优先展示成功率、P95 延迟、工具失败、校验修复/降级、用户采纳、Token 用量和单次成功规划成本。
- 先观测真实流量形成基线，再确定告警阈值和 SLO；异常告警需要带 Trace ID 与可操作的排查信息。
- 业务事件消费和可靠重试设计为持久 outbox 消费者；在持久层可用前，不以进程内事件总线替代可靠事件交付，也不宣称事件不会丢失。

验收：单次请求可通过 trace 查询主要链路；真实与估算 Token 清晰区分；成本能按模型/供应商/版本汇总；指标无高基数用户标签；告警阈值经过基线确认；持久事件消费需等 outbox 数据库迁移后做故障重试验收。

### 9.10 任务幂等、恢复与取消的代码复核补充

#### 当前实现的准确语义

- 创建任务按认证用户与 Idempotency-Key 查重；数据库迁移执行后，ai_task 的 owner_id + idempotency_key 唯一索引处理并发插入，任务进入执行前再通过 PENDING 状态 CAS 竞争执行权。
- CAS 只能避免并发执行器同时取得同一代任务的执行权，不能承诺模型供应商调用端到端 exactly-once。进程在 RUNNING 后崩溃、调用超时或确认结果前断线，都可能产生不确定结果。
- SSE GET 校验所有者，按 Last-Event-ID 重放 Redis 保留事件；终态且事件已过期时，可尝试从持久计划版本重建结果。GET 不创建任务、不发起规划。
- 只有明确检测到 ai_task 表缺失（迁移未执行）时，TaskStateStore 才退回 Redis 临时状态；普通数据库连接或 SQL 故障返回服务不可用。因此未执行迁移时仍不具备跨重启持久恢复保证。
- Outbox 现状修正：AiPlanRepository.saveCompleted 已在数据库事务内写入 ai_outbox_event，属于 Outbox 生产端；当前代码未找到对应消费、重试和派发器，因此不能声称事件已可靠送达。Redis SSE 事件不是该 Outbox 的消费者确认。
- AuthInterceptor 对 /a2a/** 要求有效认证，任务状态与 SSE 入口再校验任务 owner。此为基础用户级隔离，不等同于租户隔离或完整 RBAC。

#### 本轮编码整改项

1. HTTP 任务创建必须拒绝空白 Idempotency-Key，防止空键被转成 NULL 后绕过唯一键去重。
2. 修正数据库可用但任务只存在于 Redis 时，DB claim 更新 0 行便直接返回失败、导致任务无法启动的问题；只有确认 DB 中已有该任务且状态不可抢占时才停止。
3. 为数据库任务增加基于现有 attempt/updated_at 字段的执行租约和心跳；重复 POST 可在租约过期后重新抢占，并以 attempt 作为 fencing token，阻止过期执行器提交旧计划。该机制允许供应商调用在崩溃不确定窗口被重试，仍不承诺模型调用 exactly-once。
4. 取消改为终态条件更新；规划阶段检查取消/执行代次，计划持久化事务锁定任务并核对 RUNNING 与 attempt，避免已取消或已失去租约的执行器提交计划。若完成先于取消，取消接口应返回真实终态。
5. Redis-only 降级继续作为短期开发兜底，不宣称具备数据库租约恢复与跨重启可靠性。

#### 本轮边界

本轮不修改 data/enterprise_ai_migration.sql，不执行任何数据库迁移，也不将 Redis 降级路径宣称为生产可靠持久化。上述事件消费器、迁移与生产数据库端到端验证留待持久层阶段。

### 9.11 本轮实现、状态一致性语义与验收进度（2026-10-04）

#### 数据库与 Redis 的职责边界

- 数据库迁移执行后，MySQL 的 ai_task 与计划版本记录是业务事实来源；Redis 只承载短期任务镜像、幂等索引和 SSE 事件重放。不能把“数据库和 Redis 都成功”当成数据库提交条件，也不能依赖跨 MySQL/Redis 的普通事务实现原子提交。
- 当前计划完成事务会一起写入计划、计划版本、任务成功状态、用量、审计和一条 AI_PLAN_CREATED Outbox 事件。Outbox 事件可保证与这些数据库变更同事务提交；当前项目尚无对应的 Outbox 消费器、派发器、失败重试和死信告警，因此当前不能声称该事件已经送达下游。
- 后续 Outbox 消费应按至少一次交付设计：派发确认后再标记完成，失败可重试；下游用 event_id 做幂等去重。消费者处理成功但确认状态写回前进程崩溃时，事件可能再次派发，业务端必须容忍重复。
- SSE 事件历史存于 Redis，保留 24 小时且最多 500 条。事件可能因 TTL、容量裁剪或 Redis 故障而无法重放；Last-Event-ID 只覆盖仍保留的事件。最终计划可以从持久化版本重建，但不能据此保证所有中间 token 与工具事件永久可恢复。SSE 实时消息也不是 Outbox 消费确认。

#### 本轮已编码

1. HTTP 任务创建拒绝缺失或空白 Idempotency-Key；任务按用户与业务键复用，相同键配不同请求体返回冲突。
2. 修复 Redis 中存在任务、数据库 claim 更新 0 行时任务无法启动的问题。数据库无该任务行时仅允许带 Redis 临时存储标记的任务走 Redis claim；数据库已有活跃租约或终态时不再回退到陈旧 Redis 状态。
3. 数据库租约使用现有 attempt 与 updated_at 字段：执行器每 20 秒心跳，90 秒租约过期后，客户端用相同幂等键重试 POST 才会尝试重新 claim。没有后台扫描器；Redis-only 模式不具备崩溃后自动恢复能力。
4. attempt 作为 fencing token 贯穿进度、失败和完成写入；计划完成事务锁定任务行并核对 RUNNING 与 attempt，取消采用终态条件更新。旧执行代次不能覆盖新代次，已完成任务也不会被取消接口改写。
5. 只有明确检测到 ai_task 表缺失时，才允许 Redis 临时降级；普通数据库连接或 SQL 故障返回服务不可用，不再被误当成迁移缺失。Redis 镜像标记 MYSQL/REDIS 来源，数据库行缺失时拒绝使用过期的 MYSQL 镜像。

### 9.12 跨 MySQL/Redis 同步屏障与补偿回滚

#### 验收语义

用户要求一次计划完成作为一个业务事件处理：MySQL 计划与 Outbox 先可靠提交，Redis 未确认前不向用户返回或推送成功；Redis 确认后才对外显示 SUCCEEDED。同步超过重试预算且确认 Redis 未应用该事件时，MySQL 通过补偿事务撤销计划的业务可用状态，并继续把回滚事件投递到 Redis。

Spring 的事务注解只管理 MySQL 事务，不能在 MySQL 已提交后因 Redis 写失败回滚该事务。因此本方案提供业务层成功屏障与 Saga 补偿，不宣称 MySQL 与 Redis 组成物理上的单一 ACID 事务。Outbox 保证业务数据与待投递事件同事务提交；Redis Lua 保证 Redis 内的任务终态、幂等标记与 SSE 完成事件原子更新。

#### 实施链路

1. 计划结果、版本、审计、用量与 AI_PLAN_CREATED Outbox 在同一 MySQL 事务提交；任务进入 SYNC_PENDING，该状态不可被第二个规划执行器 claim。
2. Outbox worker 按事件 ID 幂等处理；MySQL 事务先将任务推进为数据库侧完成并将 Outbox 标记为 DB_COMMITTED。读取接口在 Outbox 尚未 SENT 时仍对外返回 SYNC_PENDING。
3. Redis Lua 一次性写入任务成功镜像、幂等投递标记和 token/task_done 事件；Redis 成功后 Outbox 标记为 SENT。接口此后才对外显示成功。若 Redis 已应用但进程未收到确认，重试依靠事件 ID 去重后补写 SENT。
4. 同步重试超过预算后，先查询 Redis 投递标记。若确认未应用，补偿事务将计划归档、任务置为失败、原 Outbox 标为失败，并创建 AI_PLAN_SYNC_ROLLED_BACK 反向事件；反向事件幂等写入 Redis 失败状态与 SSE 错误事件。
5. 若多次重试后 Redis 仍不可查询，无法区分“命令未执行”和“Redis 已执行但响应丢失”。此时保持同步待处理并记录错误日志，恢复 Redis 后先对账再决定补偿，不能盲目回滚一个已经成功写入 Redis 的事件。

#### 本轮编码边界

- 使用迁移中已有的 ai_task.status、ai_outbox_event.status/attempts/next_attempt_at 字段表达同步阶段，不修改、不执行 data/enterprise_ai_migration.sql。
- Outbox 仅派发本链路的 AI_PLAN_CREATED 与 AI_PLAN_SYNC_ROLLED_BACK 事件；其他业务事件仍由各自阶段实现消费者。
- 迁移未执行时不得把 Redis-only 规划结果报告为同步成功；AI 计划链路应明确失败或保持不可用，防止违反双存储成功屏障。
- 本地单元测试验证状态门禁、重试幂等与补偿流程；唯一索引、MySQL 行锁和 SQL 方言需迁移后通过真实数据库集成验收。
