## 1. 产品概述

### 1.1 一句话定位

Roamly 是一个把“旅行灵感、AI 行程规划、旅行笔记和社区分享”串成闭环的个人旅行工作台：用户可以用表单或对话告诉 Agent 旅行目标，得到按天组织、结合天气/地点/餐饮/预算的可执行计划，再将计划保存、编辑、记录为旅程，并选择性地分享给社区。

### 1.2 要解决的问题

1. 旅行规划信息分散在搜索、地图、天气、餐厅和备忘录中，用户需要反复整理。
2. 普通 AI 回答往往是长文本，缺少按天、按时间、按地点和预算组织的可执行结构。
3. 规划结果、出行中的记录和出行后的回忆彼此割裂，难以复用。
4. 用户想参考他人的路线，但直接复制、改写和再发布时存在来源追踪与版权风险。

### 1.3 产品价值

| 价值对象 | 核心价值 |
|---|---|
| 计划出行的用户 | 减少资料搜集与路线编排成本，快速得到符合预算和偏好的初版方案 |
| 已经出行的用户 | 将计划、照片、地点和回忆沉淀为可持续编辑的旅行内容 |
| 内容创作者 | 发布真实路线，获得点赞、收藏、评论和同好关系 |
| 平台/社区 | 通过来源链路、Agent 预检、信誉分和人工审核降低内容侵权风险 |

### 1.4 核心产品闭环

```text
发现灵感 / 收藏目的地
          ↓
表单规划 / 对话 Agent 规划
          ↓
按天查看、编辑、保存为灵感或旅程
          ↓
旅行笔记：记录、导入、配图、主题化
          ↓
发布到圈子 / 被其他用户复制和协作
          ↓
来源追踪、版权检测、社区互动
          └──────────────→ 再次形成新的旅行灵感
```

## 2. 产品目标与边界

### 2.1 当前阶段目标

1. 让用户在较少输入下生成一份结构清晰、可阅读、可保存的旅行计划。
2. 让 AI 计划可以自然进入“灵感目的地、我的旅程、旅行笔记”三个个人资产空间。
3. 提供一个可发布、可互动、可复制的旅行内容社区。
4. 在内容复制和再发布场景中保留来源关系，并提供可解释的版权治理流程。
5. 用单一工作台承载规划、编辑和浏览，减少页面跳转造成的上下文丢失。

### 2.2 当前版本不包含的能力

以下能力不应被当前 PRD 默认视为已支持，除非后续明确立项：

- 机票、酒店、门票等交易、预订、支付和订单管理。
- 对实时交通、拥堵、营业时间和价格的保证。
- 将 AI 计划直接变成导航或自动预订行程。
- 多人同时在线编辑同一篇笔记的实时协同；当前“协同”主要是源码与预览并列。
- 面向普通用户的完整平台审核后台。
- 自动推送天气、价格或出发前提醒的完整通知链路。
- 以 AI 判断替代人工或司法意义上的最终版权认定。

## 3. 用户与典型场景

### 3.1 用户角色

| 角色 | 典型诉求 | 主要入口 |
|---|---|---|
| 规划者 | 想去哪里、玩几天、预算多少，希望快速得到可执行路线 | `/chat` |
| 记录者 | 保存计划、写旅行笔记、上传图片、记录途经地点和回忆 | `/notes`、`/journeys` |
| 内容创作者 | 发布公开旅行笔记，与他人互动并维护自己的内容 | `/publish`、`/profile` |
| 灵感收藏者 | 收藏想去的目的地和他人的公开路线 | `/inspirations`、`/explore` |
| 社区贡献者 | 复制公开笔记后改写，或经作者邀请参与协作 | `/card-detail` |
| 平台审核者 | 处理高相似度、低信誉用户或举报触发的审核项 | 后端审核接口；前台暂缺 |

### 3.2 用户故事

- 作为第一次规划旅行的用户，我希望只填写目的地、天数、预算和兴趣，就能看到按天组织的路线。
- 作为希望表达更多细节的用户，我希望通过对话回答问题，而不是填写复杂表单。
- 作为计划已经生成的用户，我希望能看到每天的地点、时间、交通、餐饮、时长和费用，并知道哪些信息需要出发前再次确认。
- 作为笔记作者，我希望编辑器支持富文本/Markdown、图片、主题和预览，并能保存为自己的内容。
- 作为社区用户，我希望参考他人的真实路线，并复制到自己的空间后再编辑。
- 作为原创作者，我希望知道别人复制了我的内容，并能审核协作版本或举报疑似侵权内容。
- 作为平台审核者，我希望能看到 AI 相似度、信誉分、举报理由和完整版本链路。

## 5. 功能需求

## 5.1 账号与认证

### 功能说明

1. 用户可以使用用户名 + 密码注册和登录。
2. 注册时可选绑定邮箱；填写邮箱时需要完成验证码验证。
3. 用户可以使用邮箱 + 6 位验证码登录；未注册邮箱可自动创建账号。
4. 登录后可以绑定或解绑邮箱。
5. 用户可以登出，前端收到 401 时清理本地登录状态并回到登录页。
6. 未登录用户访问受保护页面时，应在登录后回到原始目标地址。

### 关键规则

- 登录成功返回 Token、用户 ID、用户名和过期时间。
- 验证码发送应具备频率限制、有效期和错误次数限制。
- 账号、会话 Token 和邮箱在服务端保存；前端只保存必要的登录态。
- [待确认] 是否支持密码找回、修改密码、注销账号、多个设备会话管理。

### 验收标准

- 未登录访问 `/notes` 时跳转 `/auth`，完成登录后回到 `/notes`。
- 错误密码或错误验证码不会创建重复账号，并能得到明确错误提示。
- 解绑邮箱前应确认账号仍有可用的登录方式。

## 5.2 AI 旅行规划

### 5.2.1 快速规划（固定表单）

用户在 `/chat` 的“快速规划” Tab 输入结构化目标，点击“生成专属旅行计划”。

| 字段 | 当前界面 | 当前约束/默认值 | 用途 |
|---|---|---|---|
| 目的地 | 文本输入 | 必填，最多 30 字；后端要求非空 | 确定城市/区域和搜索范围 |
| 旅行天数 | 加减控件 | 1–14 天，默认 3 天 | 生成每日计划 |
| 总预算 | 数字输入 | 300–200,000 元，默认 3,000 元 | 预算平衡和结果展示 |
| 同行人数 | 加减控件 | 1–12 人，默认 2 人 | 费用估算和偏好匹配 |
| 旅行节奏 | 单选 chips | 轻松漫游、深度人文、美食优先、亲子友好 | 决定路线密度与内容重点 |
| 兴趣主题 | 多选 chips | 美食、人文、自然、摄影、购物、夜生活 | 景点和餐饮检索关键词 |

提交后系统应：

1. 校验输入并在表单层阻止明显非法值。
2. 获取目的地天气、景点、餐饮和预算信息。
3. 按区域和时间顺序组织每日活动，减少折返。
4. 生成按天查看的计划，并展示数据来源和不可用数据告警。
5. 允许用户取消生成；失败后保留错误原因和已输出内容，并提供重试。

### 5.2.2 对话 Agent

用户在“对话 Agent” Tab 通过选项或自由文本回答问题。当前五步问题为：

1. 想去哪里旅行？
2. 想要什么旅行节奏？
3. 打算玩几天？
4. 对什么主题感兴趣？
5. 总预算大概是多少？

交互要求：

- 对话区显示 Agent、用户、工具状态消息。
- 有固定选项时显示快捷选项 chips，同时保留自由输入。
- 当前问题显示步骤进度，例如 `Q2 / 5`。
- 完成最后一步后，自动执行天气/地点/餐饮/预算整合并生成计划。
- 允许重新开始规划，清空当前问卷结果但不影响已有笔记和旅程。

### 5.2.3 生成过程与流式反馈

当前主流程使用 A2A SSE。前端应识别以下事件：

| 事件 | 用户可见反馈 |
|---|---|
| `task_update` | 显示任务开始、当前规划阶段 |
| `tool_call` | 显示正在获取天气、搜索地点、寻找餐厅或估算预算 |
| `tool_result` | 显示工具完成、结果摘要或数据告警 |
| `token` | 增量渲染 Markdown 计划正文 |
| `task_done` | 结束加载状态，展示最终结构化计划 |
| `error` | 保留已有内容，展示错误原因和重试入口 |

系统应通过 `AbortController` 支持用户取消；服务端在完成、超时和异常时释放 SSE 资源。

### 5.2.4 结果展示

结果页/结果面板至少包含：

- 目的地、总天数、总预算和计划状态。
- 按 Day 1、Day 2……切换的每日计划。
- 每天的主题、日期、天气、温度、日预算。
- 按时间排序的活动卡片：时间、类型、名称、地点、交通、预计时长、费用和备注。
- 景点/餐厅图片；图片不可用时显示占位，不阻塞计划展示。
- AI 策略摘要：天气适配、偏好匹配、路线优化、预算平衡。
- 出行提示、打包清单和整体 Markdown 说明。
- 数据来源与告警；当供应商不可用时必须明确提示“待确认”，不得将未知价格显示为免费。

### 5.2.5 结果操作

| 操作 | 当前行为 |
|---|---|
| 存到灵感目的地 | 保存目的地、计划摘要、标签、预算和封面图 | [现状] |
| 保存为我的旅程 | 创建旅程记录并写入景点点位 | [快速规划现状] |
| 继续编辑计划 | [待确认] 当前尚未形成完整的单点替换/拖拽调整闭环 |
| 转为旅行笔记 | [部分实现] 计划可保存为结构化旅行内容，编辑器迁移体验需统一 |
| 再次生成 | 使用当前条件重新调用 Agent | [现状/部分实现] |

### 5.2.6 降级和异常规则

- 天气、POI、餐饮或预算任一供应商失败，仍返回每日计划骨架，并在 `dataWarnings` 中标注来源和原因。
- LLM 输出为空、过短或缺少请求天数时，使用确定性计划文本兜底。
- 真实价格不可得时返回 `null`/“待确认”标识；不能用 0 表示免费，也不能伪造价格。
- [待确认] 是否允许用户在生成前提供出发城市、日期、住宿偏好、交通偏好、老人/儿童/无障碍等高级条件；这些字段已经存在于个人偏好模型，但当前快速规划界面未全部暴露。

## 5.3 灵感目的地

### 功能说明

用户可以创建、查看、编辑和删除“想去的目的地”卡片，也可以从 AI 计划或社区笔记中保存。

### 字段

| 字段 | 说明 |
|---|---|
| 目的地名称 | 必填 |
| 图片 | URL 或上传图片 |
| 一句话文案 | 对目的地的期待或引用 |
| 详细描述 | 目的地想法、计划摘要或个人备注 |
| 标签 | 例如 AI 规划、旅行计划、美食、人文 |
| 预估预算 | 元 |
| 最佳季节 | 春/夏/秋/冬或自定义 |
| 优先级 | 普通、想去、非常想去 |
| 状态 | 活跃、已达成/归档 |

### 交互要求

- 列表卡片支持打开详情、编辑、删除。
- AI 生成结果可以一键创建灵感目的地。
- 目的地卡片应能继续进入规划入口。
- 删除前必须二次确认。
- [待确认] 是否提供排序、筛选、达成时间线和“已去过”自动转为旅程的功能。

## 5.4 旅行笔记与编辑器

### 5.4.1 数据库笔记

数据库笔记是可保存、可分享、可发布的个人内容，核心字段包括：标题、目的地、封面、可见性、主题、状态、完整内容和社区来源帖子 ID。

编辑能力：

- 新建、打开、保存、删除笔记。
- 富文本/排版编辑：段落、标题、字号、加粗、斜体、下划线、列表、引用、提示卡片、分割线和文字颜色。
- Markdown 导入，源码/排版/预览之间切换。
- 图片选择上传、粘贴和拖拽插入；图片以 Markdown 图片语法写入内容。
- 右侧主题面板：背景色、文字色、强调色、预设主题和是否应用系统主题。
- 右侧大纲、文档信息和快捷键提示。
- 保存状态显示：保存中、未保存、已保存、已发布。
- 编辑器内链接可以在右侧网页预览面板打开。

### 5.4.2 本地源文件工作区

本地源文件与数据库笔记是两条不同数据流：

```text
本地源文件：文件句柄 → 浏览器编辑器 → IndexedDB 句柄 + localStorage 快照 → 可选写回原文件
数据库笔记：编辑器 → /api/notes → note_document/note_block → 可分享、可发布
```

要求：

- 用户可以新建本地文件工作区、打开本地文件和切换工作区。
- 浏览器支持时保存 File System Access API 句柄；句柄不可用时保留快照并提示重新授权/选择文件。
- 本地 Markdown 支持排版、源码和实时预览三种视图。
- `⌘/Ctrl + S` 写回原文件；若浏览器不支持写权限，则下载同名文件并保留快照。
- 本地源文件默认不进入数据库，也不能直接发布到社区；需先导入为数据库笔记。
- 明确提示“导入文件 = 数据库笔记；打开文件 = 本地源文件”。

### 5.4.3 分享与发布

- 笔记可以设置 private 或 link 可见性，并通过 share token 查看。
- 发布到社区前先保存一份私有数据库笔记，社区保存可展示快照。
- 社区发布失败时，私有笔记仍应保留，用户可以继续编辑和重试。
- [部分实现] 后端具备分享 token 接口，但当前前端缺少完整的分享链接生成、复制、公开访问和失效管理体验。

## 5.5 我的旅程与足迹地图

### 5.5.1 旅程记录

用户可以手动记录或从 AI 计划创建旅程。

核心字段：

- 目的地、出发城市、开始日期、结束日期、总天数。
- 总花费、旅行类型、同行人、评分。
- 天气概况、旅程总结、难忘亮点、给后来者的小贴士。
- 状态：待记录/已完成等；状态语义需统一。

### 5.5.2 路线点位与照片

- 每段旅程可以添加、删除和排序途经地点。

## 5.7 发布、复制与版权治理

### 5.7.1 发布流程

```text
用户编辑数据库笔记
        ↓
保存私有笔记 / 形成可迁移内容
        ↓
提交社区发布
        ↓
Agent 根据来源帖子做相似度预检
        ↓
结合用户信誉分进行分流
        ├─ allow → public/published
        ├─ manual_review → private/pending_review + 平台审核队列
        └─ auto_reject → private/rejected
```

原创发布没有来源帖子时可直接进入常规发布流程；复制内容发布时必须携带 `source_note_id`。

### 5.7.2 当前版权分流规则

| 条件 | 决策 | 结果 |
|---|---|---|
| 相似度 `< 0.70` 且信誉分 `>= 60` | `allow` | 公开发布 |
| 相似度 `0.70–<0.90` | `manual_review` | 私有、待平台审核 |
| 相似度 `>= 0.90` | `auto_reject` | 私有、自动退回 |
| 信誉分 `< 60` 且原决策为 `allow` | 强制 `manual_review` | 私有、待平台审核 |

### 5.7.3 信誉分与举报

- 新用户默认信誉分 100。
- 每个举报人/帖子/举报类型只记录一次，避免重复扣分。
- 当前唯一版权举报会使被举报作者信誉分扣 5 分，并记录分值变化流水。
- 举报需要保存举报理由、证据、来源帖子、AI 相似度、AI 决策和处理状态。
- Agent 负责预筛与分流，人工审核负责最终平台处置。
- 原帖在协作版本合并前不改变；合并后才更新原帖公开内容和状态码。
- 复制存档状态为 `archived`，本身不具备公开发布权限。

### 5.7.4 必须向用户解释结果

发布接口返回后，前端不能只根据 HTTP 200 显示“发布成功”，必须根据 `published`、`moderationDecision`、`similarityScore`、`reputationScore`、`reviewRequired` 和 `message` 展示：

- 已发布。
- 已提交人工审核，审核通过后公开。
- Agent 检测到高度相似，暂不允许发布。
- 发布失败，请稍后重试。

## 6. 关键业务规则与数据边界

### 6.1 身份与权限

- 所有个人数据默认只对本人可见。
- 社区公开列表只返回 `public + published + approved` 内容。
- 编辑、删除、发布、复制、评论、点赞、收藏、协作审核和举报都必须在后端再次校验用户与资源归属。
- 当前部分兼容接口仍允许通过 `userId`/`reporterId` 等请求参数识别操作者，并保留 `user_001` 默认值；这只是过渡实现，不应作为最终安全模型。

### 6.2 内容归属

```text
社区原帖 social_note.id
      └─ note_document.source_social_note_id
             └─ social_note_revision.private_note_id
                    └─ 发布成功后 published_note_id
```

复制来源必须使用帖子 ID，不得使用聊天 session、界面标签或临时状态作为版权关系 ID。

### 6.3 数据存储位置

| 数据 | 存储位置 | 说明 |
|---|---|---|
| 账号、会话、个人资料、偏好 | MySQL；验证码/会话辅助状态可用 Redis | 服务端权威数据 |
| 数据库旅行笔记 | `note_document`、`note_block` | 可编辑、可分享、可发布 |
| 通用结构化旅行计划 | `travel_note` 及关联内容 | 保存 AI/手工旅行计划模板 |
| 灵感目的地 | `inspiration` | 个人目的地收藏 |
| 旅程与路线 | `journey`、`journey_point`、`journey_image` | 出行记录和足迹地图 |
| 对话/问卷 | `chat_session`、`chat_message`、`agent_questionnaire` | 规划上下文与历史 |
| 社区内容 | `social_note`、评论、反应、好友申请 | 公开内容与互动 |
| 版权治理 | revision/report/moderation/review/reputation 表 | 来源、审核和信誉流水 |
| 本地源文件 | 浏览器 File Handle + IndexedDB + localStorage | 不属于服务器数据库，不自动发布 |
| 上传图片 | 后端文件存储目录/访问路径 | 生产环境建议迁移到对象存储或持久卷 |

## 7. 接口与系统契约摘要

### 7.1 接口分组

| 接口前缀 | 责任 |
|---|---|
| `/api/auth` | 注册、登录、验证码、邮箱绑定、登出和 Token 校验 |
| `/api/user` | 资料、偏好、头像、灵感、旅程、社区、用户和版权治理 |
| `/api/notes` | 数据库笔记 CRUD、分享查看和笔记图片上传 |
| `/api/travel-plans` | 固定格式旅行计划生成，返回结构化计划和告警 |
| `/api/travel` | 旧版文本规划、天气、POI和健康检查 |
| `/api/agent` | 对话会话、问卷 Agent 和兼容工具调用 |
| `/a2a/tasks` | A2A 任务创建、状态和 SSE 规划流 |

### 7.2 计划结果最小契约

```json
{
  "planId": "TP-XXXX",
  "destination": "杭州",
  "days": 3,
  "totalBudget": 3000,
  "estimatedCost": null,
  "budgetStatus": "待确认",
  "overview": "……",
  "dayPlans": [],
  "travelTips": [],
  "packingList": [],
  "dataSources": ["weather", "poi"],
  "dataWarnings": ["餐饮价格暂不可用"]
}
```

### 7.3 通用响应与错误

- JSON 业务接口优先使用统一 `ApiResult`：`code`、`message`、`data`、`timestamp`。
- 约定状态码：200 成功、400 参数错误、401 未登录、403 无权限、404 不存在、409 状态冲突、429 频率限制、500 服务异常。
- SSE 必须声明 `text/event-stream`，代理层不得缓冲；前端必须支持取消、超时、重试和部分内容保留。

## 8. 非功能需求

### 8.1 可靠性

- 外部服务失败时返回明确告警和可用骨架，不静默填充虚假数据。
- LLM 结果经过天数、内容长度和基本结构校验；不符合要求时使用确定性兜底。
- 长连接完成、超时、取消和异常均要释放资源。
- 保存失败时保留编辑器内未提交内容，并提供重试。
- 本地文件句柄失效时不覆盖原文件，优先恢复快照并提示重新授权。

### 8.2 安全与隐私

- Token 只通过 HTTPS 传输；服务端从已验证 Token 获取当前用户身份。
- 所有个人资源和社区管理动作进行后端权限校验。
- 富文本、Markdown 和外部图片/链接渲染必须经过 XSS 清洗。
- 图片上传限制文件类型、大小、扩展名和存储路径，避免路径穿越。
- 公开主页不返回旅行偏好、邮箱、手机号等隐私字段。
- 版权审核记录可追溯，但不将 AI 判断表述为最终法律结论。

### 8.3 性能与体验

- 规划过程优先展示首个状态事件，不让用户面对无反馈的长时间等待。
- 计划正文采用增量渲染，结果结构化后再补齐卡片和图片。
- 图片懒加载，失败时降级为占位图并继续渲染。
- 大文本编辑器超过性能阈值时暂停实时渲染，但保存必须保留完整内容。
- 主要页面支持桌面和窄屏布局；核心操作在 360px 以上宽度可用。

### 8.4 可观测性

- 记录规划任务 ID、外部工具调用耗时、成功/告警/失败来源和最终状态。
- 记录发布审核决策、相似度、信誉分变化、人工审核结果和版本关系。
- 不在日志中记录明文 Token、验证码或不必要的私人笔记正文。

## 10. 验收场景

### 场景 A：快速生成计划

1. 用户登录后进入 `/chat`，填写“杭州、3 天、3000 元、2 人、美食/人文”。
2. 点击生成后立即出现规划状态，并能看到工具处理阶段。
3. 页面在流式过程中逐步显示文本，完成后出现 3 个 Day Tab。
4. 每天至少展示计划骨架；如果天气/POI/餐饮不可用，页面显示告警和待确认提示。
5. 用户可以取消；取消后不能继续追加旧任务输出。
6. 用户可以重试，且上一次错误不会污染新结果。

### 场景 B：对话 Agent 规划

1. Agent 依次询问目的地、节奏、天数、兴趣和预算。
2. 用户可以点击选项或输入自然语言回答。
3. 最后一步后自动获取外部数据并生成计划。
4. 结果以按天卡片和正文展示，用户可以重新规划或保存结果。

### 场景 C：笔记编辑与发布

1. 用户新建数据库笔记，输入标题、目的地和正文。
2. 用户插入图片、调整主题、查看大纲并保存。
3. 用户点击“发布到圈子”后，系统先保留私有笔记，再执行社区发布和版权判断。
4. 若进入人工审核，页面明确显示“待审核”，不能误报为已公开。
5. 发布失败时，私有笔记仍可继续编辑。

### 场景 D：本地文件编辑

1. 用户新建本地工作区并打开 Markdown 文件。
2. 用户切换排版、源码或实时预览视图，编辑内容自动写入本地快照。
3. 用户按 `⌘/Ctrl + S` 写回原文件；无写权限时下载文件并给出提示。
4. 本地文件不出现在可发布数据库笔记中，除非用户主动导入。

### 场景 E：复制与版权治理

1. 用户从公开帖子点击“复制到我的笔记”。
2. 系统创建私有副本，记录 `source_social_note_id` 和版本日志。
3. 用户编辑后发布，系统根据相似度和信誉分分流。
4. 原作者在协作/修订列表中能看到来源、贡献者、状态和版本码。
5. 原作者提交版权举报后，重复举报不会重复扣分；高相似度内容自动下架，中高相似度进入人工队列。

### 场景 F：旅程与地图

1. 用户创建一段旅程，填写目的地、日期、类型、费用和总结。
2. 添加景点后自动尝试地理编码，保存后在足迹地图出现旗标。
3. 旅程可以上传或粘贴照片，并在详情页维护路线和图片。
4. 地图点位可以跳回对应旅程详情。

### 11.2 建议优先补齐的产品闭环

1. **统一身份模型**：移除生产路径中可控的 `userId`/`reporterId`，统一从 Token 获取用户。
2. **统一计划模型**：固定表单、对话 Agent、`travel_note`、`note_document` 和 `journey` 之间需要明确唯一主链路，避免同一计划出现多套保存结果。
3. **补足计划编辑**：支持替换单个地点、调整顺序、改变节奏后局部重新生成，并将修改写回笔记/旅程。
4. **补足数据透明度**：前端完整展示 `dataSources`、`dataWarnings`、待确认价格和供应商失败原因。
5. **补足分享体验**：生成、复制、撤销、失效和未登录访问分享链接。
6. **明确“协同”含义**：若不是多人实时编辑，应更名为“源码 + 实时预览”；若要做协同，需要用户邀请、权限、冲突合并和实时同步方案。
7. **补齐审核后台**：提供审核队列、原帖/副本对比、AI 结果、举报证据、人工决定和信誉操作记录。
8. **统一旅程状态**：明确“计划中、进行中、已完成、草稿、归档”的状态机，修正当前 `status=1` 的展示歧义。
9. **补齐提醒能力**：将个人偏好中的出发前、天气和价格提醒真正连接到通知渠道。
10. **补齐社区关系闭环**：好友申请的查看、接受、拒绝、取消与关系状态展示。

### 11.3 后续可考虑的能力

- 出发城市、日期、住宿和交通加入规划输入。
- 计划导出为 Markdown/PDF/日历格式。

## 12. 待确认问题清单

### 产品定位

1. Roamly 第一优先级是“AI 行程规划工具”“旅行内容社区”还是“个人旅行工作台”？
2. 首期服务范围是中国境内城市，还是需要支持海外目的地、多语言和多币种？
3. 产品是否明确面向个人自由行用户，还是也覆盖亲子、情侣、商务和团队出行？

### 规划体验

4. 计划是否需要用户提供出发城市、具体日期、交通方式和住宿预算？
5. AI 计划的最小可用质量标准是什么：每天活动数、路线距离、预算误差、数据新鲜度？
6. 用户能否对单个景点说“不喜欢”，并让 Agent 只重排当天而不是全量重算？
7. 计划与旅程、笔记之间的唯一主资源是什么？是否保留 `travel_note` 作为统一计划实体？

### 内容与社区

8. “复制到我的笔记”是个人私有副本，还是默认创建协作请求？两者入口是否需要分开？
9. 原作者是否允许关闭复制、邀请指定用户协作或限制再发布？
10. 社区帖子是公开给所有访客，还是必须登录后查看？分享链接与社区公开帖的权限是否一致？
11. 版权阈值和信誉分扣分规则是否需要运营后台可配置？
12. 平台人工审核角色、审核时效、通知方式和申诉流程是什么？
